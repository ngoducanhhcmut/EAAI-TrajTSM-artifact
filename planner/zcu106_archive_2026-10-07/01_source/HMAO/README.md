## 🚀 Quick Start

### Step 1: Get thienhau RISCV files
```bash
git clone https://github.com/thienhau/RISCV-RV32IM-Processor
cp RISCV-RV32IM-Processor/sources_1/new/*.v rtl/riscv_dcls/external/
```

### Step 2: Adjust RISCV port names
In `riscv_dcls_wrapper.sv`, the `riscv_core_wrapper` module maps to thienhau's `top.v`.
**You must verify** the exact port names from `top.v` and update accordingly:
```systemverilog
// Check top.v for exact port names:
top u_riscv_top (
    .clk    (clk),
    .rst    (~rst_n),   // Active-high? Check thienhau's reset polarity
    .i_addr (imem_addr),
    // ...
);
```

### Step 3: Check all files exist
```bash
cd hmao_project
python3 scripts/build.py check
```

### Step 4: Run simulation
```bash
python3 scripts/build.py sim          # Vivado Xsim
python3 scripts/build.py sim-questa   # QuestaSim
python3 scripts/build.py sim-vcs      # Synopsys VCS
```

### Step 5: Synthesis
```bash
python3 scripts/build.py synth
```

### Step 6: Formal verification
```bash
python3 scripts/build.py formal       # Requires JasperGold license
```

## ⚠️ Integration Notes for thienhau RISCV

| Item | Action Required |
|------|-----------------|
| Reset polarity | thienhau uses active-HIGH reset (`rst`). Our SoC uses active-LOW (`rst_n`). Already inverted in `riscv_core_wrapper`. **Verify this.** |
| IRQ port | thienhau top.v may not have IRQ input. If missing, implement RISCV firmware as **polling loop** on `HMAO_STATUS[6]` (busy bit). |
| Clock | thienhau runs 400+ MHz. We use 400MHz. **No CDC needed** between RISCV↔HMAO (same domain). |
| DCLS | Two identical instances (Core A + Core B) with 2-cycle shadow delay for glitch immunity. Voter compares outputs every cycle. |
| Memory map | RISCV DMEM address 0xA410_xxxx → HMAO RegFile (via internal bus, not AXI-Lite externally). |

## 🔑 Key Design Decisions

**Why same clock for RISCV and HMAO?**
Original spec had VexRiscv at 250MHz requiring CDC. thienhau's RISCV achieves 400+ MHz → same clock domain → eliminates RISCV↔HMAO CDC complexity. Simpler, safer.

**Why Hamming-3 FSM encoding?**
Any 1 or 2 bit-flip in state register → undefined state → watchdog catches and resets. Cannot accidentally land in a valid state after SEU.

**Why 15-stage ADMM unrolling?**
ASIL-D requires deterministic latency. No feedback loops = no variable iteration count = guaranteed bounded execution time. 15 iterations proven sufficient for ADMM convergence on this problem class.
